ISURIDE椅子を呼ぶ。その裏側を、一枚で。

03

一回の配車を追う

ライド本体は rides、状態の履歴は ride_statuses に保存します。椅子の割り当てと ENROUTE への遷移は別処理です。

Mermaid ソース 
stateDiagram-v2
  direction LR
  [*] --> MATCHING: 利用者が配車依頼
  MATCHING --> ENROUTE: 割当後、椅子が受諾
  ENROUTE --> PICKUP: 迎車地点の座標を送信
  PICKUP --> CARRYING: 椅子が乗車を報告
  CARRYING --> ARRIVED: 目的地の座標を送信
  ARRIVED --> COMPLETED: 利用者が評価・決済成功
  COMPLETED --> [*]

依頼から移動まで

  1. 利用者が見積もりを確認し、配車を依頼。未完了ライドがあれば 429 を返します。
  2. ライドと MATCHING 履歴を作成し、使用クーポンを紐付けます。
  3. 内部 API が rides.chair_id を更新。椅子は通知 API で依頼を受け取り、ENROUTE を送信します。
  4. 位置送信で迎車地点・目的地との座標一致を判定。乗車開始だけは椅子から明示的に報告します。

到着から完了まで

  1. 到着後、利用者が 1〜5 の評価を送信します。
  2. トランザクション内で評価・COMPLETED を書き込み、決済トークンで外部決済を実行。成功後にコミットします。
  3. 決済 POST が非 204 の場合は GET で件数を照合。例外時は最大 5 回再試行します。DB のロールバックと外部決済は一体のトランザクションではありません。
通知はポーリング。配車の空き判定にも関わります。

利用者・椅子の GET /notification は JSON と retry_after_ms: 30 を返します。未送信履歴を古い順に 1 件返し、app_sent_at / chair_sent_at を更新。マッチングでは、過去ライドごとの椅子向け通知済み件数が 6 件かどうかで空きを判定します。

履歴から現在値を求める

ride_statuses の最新行が現在の配車状態。chair_locations の最新行が現在位置です。オーナー向け総移動距離は、位置履歴の隣接点の距離を SQL の LAG で合算します。

設定とマスタ

settings は決済接続先などの設定、chair_models はモデル名・移動速度のマスタです。現行の Ruby マッチングは、モデルの速度や迎車距離を使って最適化する実装ではありません。

05

料金と設計上の要点

料金とクーポン

距離は緯度差と経度差の絶対値の和、つまりマンハッタン距離です。道路距離や地理座標の km 換算ではありません。

支払額 = 500 + max(100 × 距離 − 割引額, 0)
  • 初乗り 500 円は割引されず、最低支払額も 500 円です。
  • 登録時に初回クーポン 3,000 円分を付与。初回配車ではこれを優先し、その後は未使用クーポンを付与順に使います。
  • 招待登録は同じ招待コードで最大 3 人。被招待者に 1,500 円、招待者に 1,000 円分を付与します。
  • オーナー売上はクーポン割引前の料金で集計します。

ISUCON で確認したい処理

  • 繰り返し SQL: 履歴一覧・近隣椅子・評価統計で、ループ内に追加の SQL が発生します。
  • 通知の頻度: 30ms の再試行間隔を返す通知 API が、履歴参照・集計・送信済み更新を実行します。
  • 割り当て: ORDER BY RAND() と通知履歴の集計を使用。競合時の二重割り当てを防ぐトランザクションや行ロックは、この処理にはありません。
  • 決済待ち: 外部 HTTP とリトライの間も DB トランザクションが開いたままです。
  • DB 接続: Thread.current[:db] に接続を保持し、ORM を介さず SQL を直接発行します。

ここに挙げた処理はコードから読み取れる確認候補です。実際のボトルネックは、ベンチマーク・SQL 実行計画・プロファイルで判断します。

06

コードの読み順

  1. config.ru で URL と Handler の対応を確認。
  2. lib/isuride/base_handler.rb で DB 接続・例外・距離と料金の共通処理を把握。
  3. lib/isuride/app_handler.rb の POST /rides → lib/isuride/internal_handler.rb → lib/isuride/chair_handler.rb の順に配車を追跡。
  4. 利用者側の POST /rides/:ride_id/evaluation と lib/isuride/payment_gateway.rb で完了・決済を確認。
  5. lib/isuride/owner_handler.rb と ../sql/1-schema.sql で集計とデータ構造を補完。
